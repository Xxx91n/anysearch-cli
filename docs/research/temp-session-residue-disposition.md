# `.temp/` 会话残留怎么处理（#182 / #175 的 T7）

Date: 2026-11-05. 范围：issue #182 的第二件仓务动作——`.temp/` 里的会话残留。
**这份文件只写怎么处理，不是执行记录。凡是删除动作都写着「要用户单独授权」，
本票（和本实现窗口）不会删除、移动或改写任何东西。**

## 背景与边界

#182 要求对 `.temp/` 里的会话残留（#15/#16 调查文件、CI 日志、land 前备份、
评审快照）逐项给出删、存档还是留着的建议。删除动作执行前要用户单独点头；
没点头的保持原样。

**先说一个事实**：写这份方案时用的检出树（`main@4f87306`，2026-11-05）里，
`.temp/` 目录**不存在**——`git log --all -- .temp/` 在看得见的 refs 里查不到任何历史，
`git status` 没有这一项，`ls .temp/` 报 `No such file or directory`。也就是说，这些
残留没出现在 `main@4f87306` 当前能看到的 refs 的版本库里（但这不能证明它们从没在
已删除、没抓取或够不着的提交里出现过），它们属于会话或本地临时文件。
所以这份方案按 #182 / #175 写到的**类别**逐项列建议；执行前要用户在各自环境里
**先确认东西真的还在**，再单独批准删除哪一项。

> 依据 #175「待裁决」：「.temp/ 会话残留的删除授权：T7 执行时单独请示（含 land 前
> 备份的处置说法）。」——这份方案就是那个「单独请示」的书面版；用户没明确点头，
> 就不删。

## Item A — #15 / #16 的调查文件

### 已知情况（按类别说；实际文件没在检出树里出现）

- #15（api.anysearch.com 归属确认）的结论已经写进 `packages/retriever/src/providers/anysearch.ts`
  的注释块 `DEFERRED → CONFIRMED`（2026-11-04），也记在 CHANGELOG（#15 段）和
  `docs/limitations.md`。
- #16（better-sqlite3 在 macOS 退出时 mutex 崩溃）的结论已经写进
  `.github/workflows/ship-gate.yml` 的矩阵剪除、`docs/limitations.md` 和审计 S1/S2
  的修复（PR #174，已 MERGED）。
- 所以 #15/#16 的「调查文件」（探针脚本、取证草稿、对比截图等）价值已经被代码和
  文档吸收，属于可以重建的会话过程产物。

### 结论：**删（要用户单独授权）**；重建成本为零

理由：结论已经固化在代码注释、CHANGELOG 和 limitations 里，调查中间产物没有单独
保留的价值；以后要复核，证据链还在 issue #15 / #16 和对应 PR 里。如果用户要
「留个底」，退路是 `move` 到已经 gitignore 的 `.scratch/`（和 repo-hygiene-t2 的
Item A 一个标准）。

---

## Item B — CI 日志取证

### 已知情况（按类别说）

- 指在 macOS ship-gate 崩溃（#16）这类事件里抓下来的 CI run 日志或局部转储，用来
  离线对证据（比如 `eval-gate.test.ts` 抓到子进程被杀、`libc++abi` 的
  "mutex lock failed" 签名）。
- GitHub Actions 的运行历史能看多久，取决于组织的 retention 设置；删本地副本之前，
  要先确认日志还有可靠留存，或者已经单独归档。

### 结论：**删（要用户单独授权，而且先确认有留存或已单独归档）**

理由：只记着 run URL 或 run id，不能保证 retention 到期或那次运行看不了之后还能
拉回日志。如果没有可靠留存或单独归档，本地副本就得留着或归档。如果某条证据**只**
在本地有、又还没被引用，先把内容脱敏后补到对应 issue / PR 评论（按执行清单第 4 项
检查可见性），再删本地副本。

---

## Item C — land 前备份

### 已知情况（按类别说）

- 指 PR 合并（land）前，对受影响文件或分支状态做的本地或临时备份，用来在合并
  失败时回滚。
- 写这份方案时的基线是 `main@4f87306`（2026-11-05）；当时好几个相关 PR 已经
  MERGED 并稳定，land 也完成了。合并后 `main` 又往前走了，执行前要重新看当前
  `main` 的状态，别把写方案时的快照当成现在的状态。

### 结论：**删（要用户单独授权），但先确认引用它的 PR 已合并并稳定**

理由：land 成功并稳定后，回滚备份就是过期冗余。执行前逐项确认这份备份对应的 PR
已经在 `main` 里、并且通过了对应验收（比如发布冒烟检查是绿的、CHANGELOG 已记账）；
任何一个引用它的 PR 还没合并、或者还可能回滚的，这一项就**改成 keep（留着）**，
等 land 确认了再说。这就是 #175 那句「含 land 前备份的处置说法」的落点。

---

## Item D — 评审快照

### 已知情况（按类别说）

- 指 code review / CodeRabbit 处理过程中保存的快照（评审前的文件状态、diff 快照、
  评审线程的离线副本），返修时拿来对照。
- 评审线程本身还在 GitHub 的 PR / issue 上，快照只是本地多出来的一份。

### 结论：**删（要用户单独授权）**

理由：评审历史在 GitHub 上查得到，本地快照没有单独保留的价值。如果某个快照关联的
评审线程**还没关闭**、里面又有没搬走的上下文，先把内容脱敏后搬到线程评论里
（搬之前按执行清单第 4 项检查可见性），再删本地快照。

## 执行清单（给执行的人，本票不执行）

1. **先确认东西还在**：在自己的环境里确认 `.temp/` 和下面各项确实存在（写这份
   方案时 `main@4f87306` 的检出树里没有，能看到的 refs 里也没历史）。
2. **逐项批准删除**：A/B/C/D 里确认要删的，拿到用户明确授权后再执行
   `rm -rf` / `mv`；没授权的保持原样。
3. **C 项先确认 land**：删除 land 前备份之前，确认它引用的 PR 已经在 `main` 里、
   验收也过了。
4. **证据搬走前先检查**：B/D 里只在本地有的证据，先把**敏感信息去掉**（令牌、
   环境变量值、路径、个人数据），并**确认目标 issue / PR 评论谁能看到**（看的人
   不能比原来多），只搬必要内容，再删本地副本。
5. **关闭 #182**：删除授权全部落实（或者用户决定留底）后，关闭 #182；这份方案
   跟 #182 的 PR 一起进 `main`，作为处置决定的可追溯记录。
