# 知识召回排序（#283）

起始基准：`51a9ec9c9c95c6a9a1bee0966843ca2a150d0086`。
前置 #277 由 PR #287 合并，代码已在此基准里；该 PR 的远端检查全部通过。

关键词召回里的中文 LIKE、拉丁字母 FTS、其他文字 FTS 和混合文字匹配各自保留候选，再用现有 RRF 合并名次。同一条知识被多路找到时，保留各路的信号；同一路内不重复计分。不直接比较不同语言的 BM25 分数。混合查询中，中文 LIKE 在截断前先排同时命中英文部分的行，避免两路各自只留下一条单语言记录，把双语答案挤掉。

关键词结果与向量结果也用 RRF 合并，不再按固定配额拼接。对象检查仍在候选截断之前执行；有效性复查、中文 LIKE 和无向量召回均保留。不改实体阈值、向量阈值或外层各路权重。

相关度是第一排序键，只有 RRF 分数相同时才参考查询的文字类型。混合查询里的非拉丁文字优先作为提示，避免英文公司名盖过中文问题；网址和邮箱不算正文。这里只用文字类型作语言提示，不能区分同用拉丁字母的英语和法语，也不能可靠判断所有混合语言。判断不出时沿用原顺序，不过滤任何语言。

## 远端验证

正常 CI 继续跑全仓类型检查、测试和构建，包括 entity、relation、整理相关回归。新增的两个测试文件分别检查合并排序规则和单次/多次查询的实际召回行为。

`knowledge-ranking` 工作流另取起始基准和当前分支，用同一份固定数据跑实际的 `searchMemory` / `searchMemoryMulti`。数据在 `packages/store/test/fixtures/knowledge-ranking-cases.json`，中文、英文、混合查询各 4 条；不用模型、不用向量。输出每组的 nDCG@10、MRR@10、Recall@10，要求各组都不下降，混合查询的 nDCG 必须上升。原始数字和比较结果保存在 `knowledge-ranking-by-language` 构件里。

这 12 条是针对本次排序问题的小样本回归集，不能代表真实文库的整体检索质量，也没有覆盖真实向量模型质量。没有跑完远端工作流之前，不填写提升数字，不宣称验收通过。本地不编译、不跑测试和评测。

## 审查处理

CodeRabbit 首轮提出两项问题，均采纳：

- 比较脚本后接 `tee`，默认 shell 可能吞掉失败状态。评测步骤显式使用 `shell: bash`（启用 `pipefail`），再给一份故意下降的指标，验证整条管道确实失败。
- 其他文字的 crossScript 和 LIKE 回退原本缺少完整对象检查，新 RRF 会把它们的重复命中抬高，可能压过正确对象。因此在这些路径补齐 SQL 对象粗筛和截断前的精确检查；新增 Acme/AcmeCloud 前缀碰撞及三种文字混合查询回归。这里是保住 #277 已承诺的对象边界，不扩展实体识别需求。

CodeRabbit 复查又指出：固定 200 条的读取窗口仍可能被前缀碰撞填满。该意见采纳；其他文字的索引与 LIKE 回退都改成游标逐条读取，先精确检查对象，收到足够结果或候选耗尽就停止。前缀碰撞回归改为 260 条，不再用加大窗口来掩盖截断问题。

同类修复也覆盖英文严格 FTS、中文 LIKE，以及松匹配/混合文字通路：对象检查失败的前缀碰撞不再消耗候选名额。原有的相关度扫描预算保留，但在精确对象检查之后计数。测试分别加入 260 条中英俄混合、260 条英文、260 条俄文前缀碰撞，两个召回入口都检查正确行仍能返回。

CodeRabbit 第三轮的性能意见也采纳：游标不能按 `bm25(...)` 的 SELECT 别名排序，否则 SQLite 可能先用临时 B-tree 排完所有匹配行。三个知识 FTS 游标共用完整 JOIN 查询，改按 `semantic_memories_fts.rank` 排序，返回的 `rank` 数值仍取 BM25。远端测试对实际使用的 SQL 跑 `EXPLAIN QUERY PLAN`，检查严格、松匹配、混合文字和 Unicode 查询都不出现临时排序，并对比直接 BM25 排序的分数顺序与候选集合。依据：[SQLite FTS5 排序说明](https://www.sqlite.org/fts5.html#sorting_by_auxiliary_function_results)。
