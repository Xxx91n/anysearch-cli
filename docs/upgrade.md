# 换版本：四步，每一步都能单独看结果

一句话：**升级不是一个命令包办的黑箱，是四个能分别检查的步骤**。谁在干活、文件换没换、换成了哪一版、哪些入口还得重连，每一步都能单独问出来。

```
ans upgrade status   →   ans upgrade wait   →   你自己装文件   →   ans upgrade finish
     现在什么状况           暂停新任务、等收尾        npm / pnpm / 制品库        核对版本、打开准入、记下要重连的
```

## 为什么拆成四步

因为中间那步不归这个产品管。`ans` 是用 npm 装的一个包，换文件就是 `npm i -g`。产品自己去下载、自己替换自己的目录，是把自己包装成一个它并不是的东西：

- 装到一半失败，谁负责回滚？产品自己已经被换掉一半了。
- 直接改 npm 的全局目录，等于绕过 npm 的记账，下次 `npm ls -g` 就说不清装着什么。
- 已经在跑的进程不会被换掉——npm 换文件不会通知它们。承诺"热换"是假的。

所以中间那步留给用户和包管理器，前后两步由产品负责：**换之前确认没有人还在用旧代码干活，换之后确认磁盘上真的换了版本**。

## 第一步：`ans upgrade status`

看现在能不能开始换。会报三件事：

1. **准入开没开**。开着 = 新任务还能接；关着 = 上一次 `wait` 开的门还留着。
2. **有没有活没干完**。任务登记表里没写结束的行都列出来，并说清本机能不能确认那个进程还在（`还在` / `进程已不在，行没收尾` / `别的机器，确认不了`）。进程记录本身不算阻塞——常驻 MCP 服务一直在，拿它的 PID 当"活没干完"会让等待永远等不完。
3. **装的是哪一版、谁还在旧版上**。这一段见下面「两个版本」。

退出码：0 = 可以开始，1 = 还不能（准入关着，或者有活没干完）。

## 第二步：`ans upgrade wait`

关掉新任务准入，然后等手上的活干完。已经接下的请求继续跑完，包括后置的索引、审计、摘要和结算；被拒绝的请求**不排队、不事后重放**，用户重新敲一次就行。

等干净之后它做两件事：

- 写一份**暂停记录**（`~/.ans/.upgrade-pause.json`），记下"等干净的时候磁盘上是哪一版"；
- 报"可以换程序了"，**但不打开准入**。

准入由 `finish` 打开，不由 `wait` 打开。`wait` 自己打开，等于在"可以换"和"换完了"之间留一个谁都能进来的窗口。

等不完（`--timeout`，默认 120 秒）就退 1，列出还挡着的活，一个文件都不动。处理不了的可以 `ans upgrade dismiss <taskId> --reason "..."` 记一笔，或者 `ans upgrade cancel` 放弃这次暂停。

## 第三步：你自己装文件

`ans upgrade` 不换自己的程序文件：不下载、不安装、不重启任何进程。用什么装由你定：

```
npm i -g @anysearch-cli/cli@latest
```

旧的多包安装要先换掉，见下面「旧布局怎么换」。

> 唯一的例外是 `ans upgrade install`：它会在预览之后卸掉旧布局里那几个独立的全局包（要取代的旧包，不是本产品自己的文件）。默认只预览，删之前先写恢复记录，认不出归属的一个都不动。

## 第四步：`ans upgrade finish`

文件装完再跑。它做的事：

1. 拿现在的磁盘版本和暂停记录里的那一版比。**一样就拒绝**：说明 npm 那步没成功，文件根本没换，这时候报"升级完成"是假的。准入继续关着。
2. 不一样就写一条**换版记录**（`~/.ans/upgrade-history.json`，留最近 20 条）：从哪版到哪版、什么时候、哪几个入口还在旧版上。
3. 打开准入，清掉暂停记录。
4. 报出还得重连的入口，以及旧库副本还在哪（**只说不动**：拿旧快照恢复会丢掉换版之后写进去的数据，这不是一条命令该替人做的决定）。

没有暂停记录时它不给基准，明确拒绝——没有"从哪一版停的"，就核对不了到底换没换。

## 两个版本为什么要分开报

这是最容易说错的地方。

- **磁盘版本**：`<包根>/dist/build-info.json` 说的是哪一版，也就是**下次启动**会用哪一份代码。
- **执行版本**：某个进程自己记下的那一版（任务登记表的 `build` 列，进程启动时写一次，之后不改）。

一个常驻 MCP 服务可以活过整场升级：磁盘早就换成 0.2.0 了，它执行的还是 0.1.2 的代码。只报磁盘版本，等于把"装好了"说成"已经在跑新版"。

所以 `status` 把两边的都报出来，并把不一样的入口列成「待重连」，三态分清：

| 状态 | 意思 |
| --- | --- |
| 跑的是旧版 | 记下的构建和磁盘上不一样，重启或重连才会换 |
| 没记是哪一版 | 旧版本没有这一列，说它是旧版是猜的，说它是新版更是猜的——单独列出来 |
| 跑的就是这一版 | 不用管 |

按 D1，换版本靠**重启或重连**，不承诺透明热换。产品不重启任何进程：什么时候重启由你决定。

## 旧布局怎么换

0.2.0 以前是三个全局包各装一次（`@anysearch-cli/cli`、`@anysearch-cli/mcp`、`@anysearch-cli/plugin`），三个包往同一个全局 bin 目录里写命令。`ans-mcp`、`ans-plugin-server`、几个钩子命令的名字被两个包同时声明，谁最后装谁赢——于是"装的是哪个版本"和"命令实际指向哪个包"可以不一致。

```
ans upgrade install              # 只看：谁装着、每个命令指向谁、建议怎么换
ans upgrade install --apply      # 真执行：卸掉旧布局的独立包
```

判定分四种：

| 判定 | 意思 | 能不能动手 |
| --- | --- | --- |
| `clean` | 只有一个完整产品，命令都指向它 | 没什么要做的 |
| `legacy` | 旧包还在，或者命令还指着旧包 | 能，按方案卸旧包 |
| `blocked` | 有命令认不出归属，或两个包都声明了却定不下来 | **不能**，一个包都不删 |
| `absent` | 这个前缀里没装过 | 不替人装 |

**认不出来就不动。** 命令指向的东西认不出是哪个产品包（你自己写的 `ans` 脚本、别的工具），报出来，一个文件都不碰。把别人的 `ans` 删掉，比留着一份旧安装糟得多。

**先写恢复依据再删。** 动手前的完整现场（谁装着、每个命令指向谁、判定和方案）先落到 `~/.ans/install-migrations/<时间>.json`，写不进去就不执行。

### 新命令用不了的时候

旧包的 `ans` 还占着名字、新包的 bin 还没链上、或者装到一半——这时候不能指望 `ans upgrade install` 能用，那正是要走这条路的原因。照文件路径直接跑：

```sh
node "$(npm root -g)/@anysearch-cli/cli/dist/migrate-install.js"
```

```powershell
node "$(npm root -g)\@anysearch-cli\cli\dist\migrate-install.js"
```

参数和 `ans upgrade install` 完全一样（同一段代码），包括 `--apply`。这条路不加载主程序，只碰 node 内置模块，所以起得来就不依赖任何全局命令是否已经链好。

## 出问题的时候

| 现象 | 发生了什么 | 怎么办 |
| --- | --- | --- |
| `finish` 说"文件没换" | 装文件那步没成功，磁盘上还是同一版 | 装完再跑一次；要放弃就 `ans upgrade cancel` |
| `finish` 说没有暂停记录 | 没跑过 `wait`，或者记录被删了 | `ans upgrade wait` 重走一遍，或 `cancel` 直接开准入 |
| `status` 说准入关着但没人在升级 | 上一次 `wait` 被 Ctrl-C 打断了 | `ans upgrade cancel` 打开准入 |
| `install` 判 `blocked` | 有命令认不出归属 | 先看清那个命令是谁的；确实是本工具的才处理 |
| 换了版本但入口还在跑旧代码 | npm 换文件不会通知已经在跑的进程 | 重启宿主，或让它重连 |

## 这次没覆盖的

- **打包产物那条路只由 CI 的安装验收跑**。本机验证的是源码路径上的单文件测试（迁移判定、换版核对、进程登记），没有跑过装出来的 `dist/migrate-install.js`；`scripts/installed-acceptance.mjs` 里那条腿由远端 CI 执行，本机没有构建。
- **其他平台没真跑过**：Windows 以外的 npm 全局前缀布局和 shim 形态（POSIX 的符号链接、`<prefix>/lib/node_modules`）按代码里的分支处理，没有在真实机器上验过。
- **真实旧包没试过**：迁移判定用临时目录搭出来的假安装验证，没有拿线上真实的 0.1.2 / 0.2.0 三个包跑一遍。
- **不自动升级**：没有"发现新版本就装"的行为，也没有后台检查。
- **不强杀任务**：等不完就报阻塞，不替你结束进程。
- **不承诺热换**：宿主是否支持自动重建按各宿主的验证记录报，不外推。
- **不自动恢复旧快照**：可能丢数据的恢复一律不自动执行。
- **手工替换 npm 目录不算受管升级**：直接改 `node_modules` 的人不走这套协议，产品也不替他保证。
- **宿主配置里的命令路径不在本命令的迁移范围**：那是接入流程的事（`ans host status` / `ans host repair`），`finish` 只提醒一句。
