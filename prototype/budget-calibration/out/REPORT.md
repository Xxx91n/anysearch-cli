# Q2(d') 输出侧静态预留（outputReserveTokens）缺省校准 — 原型结论

数据：43 次独立真实 run（`ans chat` 生产入口，真实 LLM + Active Domain + 记忆接线），
2026-11-05，模型 `openai/deepseek-v4.1-flash`（单次调用 maxTokens=8192）。
原始样本：`out/raw.jsonl`；统计：`out/summary.json`；跑批日志：`out/run.log.txt`。

## 一、结论（交主窗口裁决）

**缺省建议：`outputReserveTokens = 12288`，可接受区间 `10240 – 16384`。**

理由（按证据，不按直觉）：

| 观察 | 数值 |
|---|---|
| 每次 run 的输出 p50 | 3,948 |
| p90 | 8,122 |
| p95（n=43） | 9,309 |
| 样本最大 | 9,600 |
| 12288 覆盖 | 43/43，对样本最大留 28% 余量 |
| 12288 = | 3.1 × p50；≈ 1.28 × 样本最大；1.5 × 单次调用 maxTokens |

- **不能取 8192（= 单次调用上限）**：43 次里有 4 次（9.3%）输出超过 8192，最高超 1,408。
  这正是「预留过小 → cap 实际变软」的实测形态：reserve 放行后 settle 必超。
- **不宜再大（16384+）**：p50 只有 3.9k，16k 的预留下，每个合法 run 平均白占
  11.6k 的 cap 窗口；LiteLLM PR #27539 的教训是预扣必须有界，不是越大越安全。
- **偏向大侧的依据（Q4 不对称）**：拒绝可恢复——`domain reloader` live-mtime 让提额
  下一轮即生效（pause 非 terminate）；超支不可逆。所以在 10k–16k 里取偏大值 12288。
- **为什么给区间不给裸点值**：n=43 时样本最大作为「95% 覆盖率」界的置信度只有
  1 − 0.95^43 ≈ **88.9%**，tolerance bound 需要 n≥59 才到 95/95 口径。点在 12288，
  区间留 10240（零超支的最小整数候选）到 16384。

## 二、分布证据

### 全样本（n=43，output 单位=token）

| 指标 | min | p10 | p50 | mean | p90 | p95 | max |
|---|---|---|---|---|---|---|---|
| output | 167 | 2,209 | 3,948 | 4,744 | 8,122 | 9,309 | 9,600 |
| input¹ | 69 | 10,356 | 41,120 | 38,620 | 60,839 | 64,574 | 75,238 |
| input+output（总量下限） | 236 | 13,226 | 44,712 | — | 68,938 | 70,276 | 81,243 |

¹ `usage.input` 不含 cacheRead/cacheWrite；settle 的 `totalTokens` 含。输出侧校准不受影响。

### 按条件

| 条件 | n | output p50 | p90 | p95 | max |
|---|---|---|---|---|---|
| docs（rag=none） | 15 | 3,751 | 6,326 | 6,632 | 7,240 |
| research（rag=none） | 15 | 6,103 | 9,434 | 9,505 | 9,600 |
| default（rag=none） | 6 | 4,308 | 5,790 | 5,968 | 6,146 |
| docs + RAG fts（原型域） | 7 | 3,118 | 3,634 | 3,761 | 3,888 |

- 重头是 research：p95 9.5k，单条 toml 域上限（无 cap）下也不是无限长。
- RAG 注入（fts）没有抬高输出，反而更低——它主要抬高/改变输入与首答路径；与「静态输出
  上限按输入动态部分无关」的 Q2(d') 结构一致。
- 因此缺省值必须按 **research 这类重域**定，不能按 docs/fts 的轻域定。

### 双向风险的量化（R 为候选预留值）

| R | 输出超 R 的 run（cap 变软） | 最大超支 | 合法 run 的白占窗口（R − 实际，中位） |
|---|---|---|---|
| 8,192 | 4/43（9.3%） | +1,408 | 3,912 |
| 10,240 | 0/43 | 0 | 5,496 |
| **12,288** | **0/43** | **0** | **7,544** |
| 16,384 | 0/43 | 0 | 11,640 |

「白占窗口」= 剩余额度落在 [实际, R) 时会被误拒的区间；它是「预留过大」的成本。
12,288 在样本上消除了超支，同时把误拒窗口压到 16,384 的约 2/3。

## 三、方差（判读约束的复核）

同一 query、同一条件重复运行的输出比：

- 中位 **1.83×**，最大 **2.74×**（剔除下方两个异常样本后）；
- 与预注册实证研究的 1.55×（中位）/2.86×（p90）同量级。

结论：单次采样不足以定尾，这也正是「区间优先、n 要够」的原因；不要把 12,288 当成
分布上界，它只是本样本下的有界缺省。

## 四、数据卫生：两个异常样本

| run | 输入/输出 | 现象 |
|---|---|---|
| r14（research） | 19,252 / 679 | 53s 完成，输出极短，像提前收束 |
| r16（research） | 69 / 167 | 21.8s 完成、exit 0、打印了 done——但输入只有 69 token，疑似空响应/上游异常 |

两者只影响 p10，不影响 p95/max 与结论。r16 的形态（exit 0 + done + 近零 usage）对
**settle 记账**有意义：它会被记为「合法但极省」的 run。是否需要在生产侧把这种 run
单列，超出本实验范围，仅记录。

## 五、口径与边界（不外推）

- **单模型、单端点、单机**：换模型（尤其调大 per-call maxTokens）需重测；建议维持
  `R ≈ 1.5 × per-call maxTokens` 的关系，当前 1.5×8192 = 12288。
- **43 个独立 run**；固定 10 条 query × 2 轮，加 fts 变体 2 条 × 2 轮。采样期间两个
  采样进程曾并行写库（非计划），但每 run 唯一 `ANS_SESSION_ID`，token 计数不受并发影响。
- **只定输出侧静态上限**：输入侧（实测 occupancy）、USD（settle-only）、cap 的默认值
  与 TOML 形状均不在本实验结论内。
- **副作用**：43 个 session 行与消息/记忆写入 `~/.anysearch/anysearch.db`，清理需显式授权。
