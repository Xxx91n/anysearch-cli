# AGENTS.md — anysearch-cli

AnySearch is an agent CLI (`ans`) that works inside one domain only. It keeps retrieval results tied to their sources, filters them against a strict domain allowlist, and says there is nothing to answer when no results pass the domain filter. Answers that a provider generates itself (for example Exa or Tavily answer mode) do not pass through this filter and are marked unverified. `GLOSSARY.md` is the only place to look up what a term means.

## How to run
- `pnpm install --ignore-scripts` — install dependencies. better-sqlite3 ships a prebuilt binary, so no node-gyp.
- Source MCP development uses the complete product build: run `pnpm -C apps/cli build` before the first `pnpm -C apps/cli dev mcp --help`, and rebuild after MCP or hook source changes. The `dev` script does not build automatically.
- `pnpm -r check` / `pnpm -r test` / `pnpm -r build` — run the same task in every package (turbo). `apps/cli` and `apps/plugin` build what their tests read, so `pnpm -r test` is green from a clean checkout too: `apps/plugin`'s `pretest` compiles `dist/` only, and `apps/cli`'s `pretest` builds the complete product into its own directories (`ans mcp` forwards to its packaged MCP launcher). Caveat: the root `pnpm test` runs turbo, whose `test` task depends on `build`; that `build` still runs `gen:configs` first, so a hand-edited generated file is rewritten before any test reads it. The drift check still catches a hand edit because it compares the generator's output with `HEAD`, not the working tree: the edit only shows up once it is committed, and from then on it is red from every entry point. This dependency is older than #256 and unchanged here.
- `pnpm gate` — the merge gate: `turbo run check` then the full suite. Run it on a tree that already contains the current `origin/main`; see `### Gate rules` for what does and does not count.
- `node scripts/dep-age-status.mjs` — answer "why does install reject the lockfile". It lists dependency versions inside the release-age window (`minimumReleaseAge` in `pnpm-workspace.yaml`) and prints the moment the last one clears. Exit 0 = the lockfile passes; exit 1 = something is blocked (too young, or no publish time); exit 2 = the registry lookup failed. Waiting is the fix; `PNPM_CONFIG_MINIMUM_RELEASE_AGE=0` only hides the check locally.
- `node scripts/ship-gate.mjs` — release smoke check. It runs checks, build, packaging, a real install and a real start, and its answer decides whether the release is good.
- `node scripts/installed-acceptance.mjs` — 包装好以后到底能不能用。它启动装出来的 MCP、跑一轮 `ans_chat` 再续一轮、整理选定的材料、让另一个会话召回内部搜索写进去的东西、打开一个旧一点的库（迁移、行还在、再迁移一次）。模型是本地假端点，验的是接线和记账，不是模型判断得好不好。`ANS_ACC_TARBALLS=<目录>` 直接装那个目录里的包，不用本地编译。没有搜索 key 时那一条打 SKIPPED。CI 里作为 `install-smoke` 的两步跑（车道本身 + 一条不需要 key 的解析器自测：`node scripts/installed-acceptance.mjs --self-test-parser`）。
- `pnpm -C packages/store eval --offline` — offline run of the fixed memory test set.
- `node scripts/dsh-approval-acceptance.mjs` — real-host check of the dsh approval channel (allow once, reject, cancel, headless no-channel). It builds its own temp `DSH_HOME`, workspace, servers and model patch, then deletes them on exit; `--keep` leaves the sandbox. Needs Node 22.15+ (zstd session logs), `ANS_LLM_BASE_URL`, `ANS_LLM_API_KEY`, `ANS_LLM_MODEL`, plus `ANS_ACCEPTANCE_PLAYWRIGHT` (module or directory) and optionally `ANS_ACCEPTANCE_BROWSER`. `DSH_BIN` picks the host; no version is pinned.
- Push gate install: `pnpm hooks:install` at the repo root (`pnpm -w hooks:install` from a subdirectory — pnpm only finds the script in the package that declares it). It copies `scripts/hooks/pre-push-user` into the hooks directory git actually reads (`.git/hooks`, or `core.hooksPath` when that is set), adds the execute bit on POSIX (a Windows hook needs none), and removes the old `pre-commit-user`. Running it again changes nothing, and it never touches GitButler's `pre-commit`. A `pre-push` that is not ours is left alone unless you pass `--force`; an empty one is replaced.
- Push gate status: `pnpm hooks:status` exits 0 when the hook is in place and runs the same commands as the source; when it is missing, out of date, not executable, or someone else's, it exits non-zero and names which; outside a git repo it exits 2. When the hook is healthy it also prints which mode a push of this checkout would land in — advisory (a change no package owns only warns), incremental (a package change, or a root file whose readers run), or full (`ANS_PUSH_GATE=strict` or `--full` in the hook) — or that nothing would run, plus what waiting for that run costs; a change set git cannot name prints `mode: unknown` and still exits 0, because the hook is fine and a push runs what its refs carry. It exits 2 instead of printing a mode when the gate script the hook runs is missing, does not parse, imports a file that is gone, or the repository cannot be planned: a gate that cannot run is nobody having looked, not a red test. The same exit 2 covers the rare hook whose own exec line is a shape status cannot follow, and that one means the line in `scripts/hooks/pre-push-user` needs repairing: the installed copy matches it, so reinstalling alone changes nothing.
- `node scripts/preflight-test.mjs --dry-run` prints the plan; `--full` runs everything. Every test run points `HOME`/`USERPROFILE` at a throwaway temp dir and drops the repository pointers (`GIT_DIR` and the rest), so a test that forgets its own sandbox writes there instead of your `~/.ans`, and a test that makes its own repo cannot commit into your checkout; a green run deletes it (or says it could not), a red one keeps it and prints the path. The suite itself runs under a budget of `ANS_PUSH_GATE_TIMEOUT` seconds (600 by default), prints a heartbeat every 15 seconds while it runs, and writes the whole output to a timestamped file in the temp dir, named with one of three labels: `full output` when the run ended, `partial output (the run did not finish)` when its budget or a signal cut it, `incomplete output file` when the write failed. A red, timed-out or interrupted run keeps that file, a green run deletes it. What runs at each step is under "Gate rules" below.
- The gate's own tests, three groups: `node --test "scripts/test/preflight-*.test.mjs"` covers the gate's rules — which files a push carries, which packages that selects, which root files have readers, which unowned files skip with a warning, which broken trees stop with exit 2, which files count as documentation, what a red or timed-out run prints, which home the child gets, which repository git reads inside a test, that a red self-test blocks, and that `hooks:install` / `hooks:status` put the right file in place and name what is wrong when they cannot. `node --test scripts/test/ci-changes.test.mjs` and `node --test scripts/test/check-workflows.test.mjs` cover the shared judgments: CI's change policy (which lanes a change reaches) and the workflow checker (#487). CI runs all three in `check-build`, and a full gate run (`--full` or `ANS_PUSH_GATE=strict`) runs each group as its own run. The gate names each group and, when it passes, how many tests ran; a red group blocks the push before the suite starts. Incremental, docs-only, and unowned pushes skip all three groups locally (even changes under `scripts/` — the self-test takes ~1m46s and does not fit a pre-push budget; CI's `check-build` covers them).
- `node scripts/check-skills.mjs` — every `SKILL.md` Git can see (tracked, plus new files that are not ignored), checked against the agentskills.io rules the product enforces: frontmatter is a mapping, `name` is 1–64 lowercase letters/digits with single hyphens (not a Windows device name) and equals its directory, `description` is 1–1024 characters, body stays under 500 lines; a missing "when to use it" clause is a `note`, not a failure. It calls the same `validateSkillFile` / `validateSkillDirectory` that `ans skill install` and `ans skill validate` use, so all three give the same verdict — except on `name` equals its directory, which install skips on purpose (a cloned repo's folder carries its own name) and validate and this script enforce. Exit 1 = a skill broke a rule or nothing was found; exit 2 = the check could not run. Pass a directory or a `SKILL.md` to check just that one; CI runs it in `check-build`.

### Gate rules (#367, #671 — a commit, a push, a merge)

**Who does what:** the local push gate is for catching mistakes early; seeing CI's `check-build` go green before merging is what clears a merge. The local gate is not a mechanical enforcement point and no longer falls back to the full suite.

Three steps, three different amounts of testing.

- **A commit runs no tests.** There is no commit hook in the repo, so fixing a message or splitting a commit costs no test run.
- **A push runs the local gate for fast feedback.** It fires for `git push` and `but push`, and `planPreflight` in `scripts/preflight-plan.mjs` decides what happens:
  - **Package changes (`incremental`)**: runs the changed workspace packages plus every package that depends on them, tests only (never `turbo run check`, so it cannot catch type drift on the base branch — that is the merge gate's job, #480). One package keeps the upstream-test edge: `@anysearch-cli/dsh-plugin#test` depends on its dependencies' test tasks, because its tests read `apps/plugin`'s built hook bundles and `apps/plugin`'s `pretest` rebuilds `dist/hooks` — side by side, the test reads a half-written directory (#490). Every other package runs only its own tests.
  - **Root files with known readers (`readers`)**: `ROOT_READERS` in `scripts/preflight-plan.mjs` lists root files whose readers are pinned by tests — not by a build copy, since turbo caches builds and a root-only change never enters that hash — today `domains/*.toml`, the root `eval-*.json` records, and the root `AGENTS.md` (which store's docs-golden test needs on disk even though nothing reads the prose) (#489). Changing one runs only those reader packages with no dependents.
  - **Documentation only (`docs`) and unowned files (`unowned`) — skip, never pass**: a push carrying only `docs/` (except `docs/eval/`) and the four root markdown files (`README.md`, `README.zh-CN.md`, `GLOSSARY.md`, `CHANGELOG.md`) asks `isDocumentation` in `scripts/preflight-plan.mjs` (the same function CI asks), runs nothing, prints `skipped`, and exits `0`. A docs-plus-code push drops the docs and still runs that code's packages. Anything else outside the workspace packages — `scripts/`, the lockfile, `package.json`, `turbo.json`, `pnpm-workspace.yaml`, `.github/`, `.gitignore` — is `unowned`: the hook runs **no tests** (even if the same push also touched a package), prints `skipped` naming why it skipped, which files had no owner, and that CI's `check-build` owns that coverage, and exits `0`. **The old contract still holds: a skipped run is never a pass.** Neither `docs` nor `unowned` prints green, and neither is evidence that the change is good. To force the whole suite locally anyway, run `node scripts/preflight-test.mjs --full` or set `ANS_PUSH_GATE=strict`.
  - **Broken repository or unreadable push (`broken`) — stop, exit `2`**: when the gate cannot read the tree or change set — unreadable or invalid `package.json`, a `package.json` missing `name`, missing/unreadable `pnpm-workspace.yaml`, a `ROOT_READERS` entry naming a package that no longer exists (`no workspace package named:`), or refs git cannot read — it runs no tests, prints `blocked`, the reason, the fix (for unreadable refs, run `git fetch origin`, then `git remote set-head origin -a` if `origin/HEAD` is still missing), and the escape hatch `git push --no-verify`, then exits `2`.
  - **Exit codes**: `0` = skipped or passed; `1` = tests failed or did not finish (timed out); `2` = the gate itself is broken (could not read the repo, could not read the change set, bad `ANS_PUSH_GATE_TIMEOUT`, or could not start `pnpm` / self-tests — meaning nobody looked, not that the code is red; `pnpm hooks:status` uses `2` the same way). `SIGINT` / `SIGTERM` keep their signal codes (`130` / `143`).
  - **Tool `timeout` rule**: whenever a tool or agent runs a push, set the tool's `timeout` to `0` (no cap) or `>= 600` seconds; when running the full suite (`--full` or `ANS_PUSH_GATE=strict`), set it to `0` or `>= 900` seconds. Reason: `store` alone takes **4m15s** (4 minutes 15 seconds) on a normal run (and the full suite takes 6–9 minutes on Windows), so a default 300-second tool timeout kills a run that would have passed and makes it look like a red gate. The hook enforces its own budget via `ANS_PUSH_GATE_TIMEOUT` (default `600` seconds): hitting it kills the whole process tree, keeps the output file, and exits `1` (never a pass).
- **A merge must wait for `check-build` to be green — plus one current-base run, unless the PR is docs-only.**
  - **You must see `check-build` green before merging.** Not "try to remember" — if `check-build` is still running, skipped unexpectedly, or red on the current head, do not merge. **Be honest about how this is enforced: no machine enforces it.** `main` has no required status checks, so GitHub will let you merge while CI is running or red. Since the local push gate no longer runs a full-suite fallback for unowned files, holding this line before merge is entirely on the person merging.
  - Before every merge, rebase the branch onto the current `origin/main`, run `pnpm gate` locally (`turbo run check` plus the full suite), wait for it and `check-build` to pass, and merge straight away. A green run on a tree that does not contain the current `origin/main` does not count: two PRs can each be green on their own base and still break the merged tree, because tests run through `tsx` and never typecheck (#480). Do not merge while `main`'s latest push run is red.
  - The one exception is a PR whose whole change set is documentation (`isDocumentation` in `scripts/preflight-plan.mjs`): `docs/` (except `docs/eval/`) plus `README.md`, `README.zh-CN.md`, `GLOSSARY.md`, `CHANGELOG.md`. `apps/plugin`'s markdown and `domains/docs.toml` are product assets; `docs/eval/` is evaluation evidence — tests read both, so neither counts as documentation. CI asks the same function in `.github/actions/setup`: a docs-only PR skips every lane and needs no extra full run before merge. For code changes, CI skips lanes whose declared packages in `LANES` (`scripts/ci-changes.mjs`) the change cannot reach; a push to `main` or manual dispatch runs every lane. A root-file or unowned change runs every CI lane (including `check-build`, which lists all eight workspace packages in `LANES`). Lane selection only saves CI minutes — it does not replace a current-base run before merge, and a green incremental push only covers the packages it touched.

Branch protection on `main` blocks merging only while a review conversation is unresolved (`gh pr merge` refuses with `base branch policy prohibits the merge`); `enforce_admins` is off, so `--admin` can bypass that. `required_status_checks` is intentionally empty, and locally `--no-verify` (or a ref delete) can bypass the pre-push hook. Three things are on record here:

- **We considered making `check-build` (ubuntu and windows) required status checks on `main` and decided not to (#671, #674).** `check-build` already lists all eight packages in `LANES` (`scripts/ci-changes.mjs`), so every non-docs change already runs the full suite in CI — making it a required check would not close any coverage gap. For a solo repo where the maintainer already reads CI before merging, required status checks only prevent accidentally clicking merge while checks are still running, at the cost of tying every merge to CI stability (any CI flake blocks merging). Checking CI before merge stays a human discipline recorded here, not a repository setting.
- Earlier, when the repo was private, we also rejected making it public or paying for a higher GitHub plan just for branch protection (#58, #59). The repo is now public and required status checks would be free, yet we still choose not to turn them on for the reason above.
- #67 showed, by pushing a commit that was meant to fail, that the pre-push hook really does block a push unless you pass `--no-verify`. Proof: [the closeout comment on #67](https://github.com/Xxx91n/anysearch-cli/issues/67#issuecomment-6431860529).

`spaced-path` (#358) is advisory: it is not in `.github/workflows/release.yml`'s wait list or `FAMILIES` in `scripts/check-runs-verdict.mjs`, so a red run does not stop a release.

## Directory conventions
- `packages/{kernel,store,retriever,embedding}` are shared libraries. `apps/{cli,mcp,plugin,dsh-plugin}` are the four ways users run the tool. `GLOSSARY.md` is the word list. `docs/agents/` holds notes for agents.
- `providers/` holds per-provider notes and manual probes, one subfolder per provider id (`exa`/`tavily`/`anysearch`); a probe runs with plain `node <file>` from the repo root and stays out of the build. The one file at the root, `providers/probe-credentials.mjs`, is shared by all three probes: the `.ts` loader hook, the one `resolveSearchCredentials` call, and the value mask.

## Docs
- When a doc points at another place, write the file plus the section heading or the symbol name (`classifyProviderError`, `## Directory conventions`), never a line number: the line moves as the file grows and nothing turns red when it does (#420).

## Gotchas (not visible in the code)
- better-sqlite3@13 loads a prebuilt `.node` file. `allowBuilds: false` in pnpm-workspace.yaml is on purpose. Turning it on would need MSBuild + ClangCL. Leave it.
- pnpm is pinned to 11.24.0 with `pmOnFail: error`. A version mismatch stops at once and never rewrites the lockfile. Change both pinned fields in one commit.
- All version control goes through GitButler (`but`). Never push without an explicit order.
- Each host's hook format has its own trap. Codex accepts only the `hookSpecificOutput` shape. Antigravity sends camelCase JSON on stdin, and on `PreToolUse` an empty `{}` means DENY. The rest are listed in `docs/*-integration.md` and in the comments under `apps/plugin/src/hooks/adapters/`.
