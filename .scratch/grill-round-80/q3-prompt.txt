## 待裁问题

首发路径三选项：
- A 预首发：用户即刻手动 npm publish @anysearch-cli/dsh-plugin@0.0.7 → 配 trusted publisher → R80 落 pack 清单接入+0.0.8 sync-bump → tag v0.0.8 五包统一 OIDC（0.0.8 起带 provenance）。
- B 随车首发：v0.0.8 tag 直接含 dsh-plugin——需 publish 腿幂等跳过（npm view 判存在）或首发走例外路径，版本碰撞风险。
- C 仅手发本轮：pack 清单接入递延 R81，v0.0.8 自动化面不含 dsh-plugin。

## 调研问题

工业界成熟落地心智模型下：(1) npm OIDC trusted publishing 对「尚不存在的包」的行为边界——npmjs 官方文档对 first publish / new package / trusted publisher 预配置的准确语义是什么？新包首发有哪些被官方支持的自动化路径（granular access token / OIDC / 手动），各自的 provenance 与安全后果？(2) monorepo 中新成员包加入既有 release train 的成熟模式——预首发（pre-publish）vs 幂等 publish step（skip-if-exists）vs 单独首发轨，业界（changesets/pnpm publish -r/手搓 workflow）惯用哪种，踩坑点是什么？(3) 对本仓 A/B/C 给出推荐与理由，含被否选项否决理由；同时评估「预首发 0.0.7 无 provenance」的后果等级（对照 0.0.3 先例与 sigstore 覆盖起点惯例）。
