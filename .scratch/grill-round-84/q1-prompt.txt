背景（R84 主轴裁决调研）：信息专精 Agent CLI 仓库（TypeScript monorepo：packages kernel/retriever/store + apps cli/mcp/plugin/dsh-plugin），刚落地「垂直领域贯通」轮（ADR-0084）：SearchRequest.vertical{domain,subDomain?,params?} 双层贯通（仓 TOML sources.vertical 亲和默认+工具 arg 查询级整体替换，无深合并）、能力协商 hint 扇出（verticalDomainSupported 位；不支持 provider 照常扇出+审计具名 degraded；post-filter 权威闸不动）、retrieval.vertical.pre 独立审计事件（params 只记键名不落值）、形状校验+服务端真理（不内置枚举/get_sub_domains 不进运行时/非法组合→isError→fail-first 降级）。既有心智模型锚：多 provider 扇出+融合层归并、充分性门（sufficiency gate/MVSS）、已有离线 eval 基础设施（金标集/归因校准/开关状态机家族）、Goodhart 对称警惕（无启用判定的证据=仪式化残留应删）、「记录的记录」类已被派生件新鲜度腿机器接管。延期注册表现存：prefer-capable 加权调参（注记前置=eval 数据证明垂域臂召回质量差异，eval 数据驱动非契约职责）；dsh ≥0.1.7 宿主侧 live 验收（unverified-at-host，需用户侧宿主升级或垫沙箱）；审计返工候选池七项（校验三入口不匀/CLI flag 吞词/空 params 对象 wire 语义/三处垂域组装重复/证据文档命令前缀/存量死参数 maxResults/审计键漂移披露复核）。R84 主轴候选：(A) 垂域 eval 面——建垂域召回质量评测腿，产出「垂域路由是否改善答案」的质量证据（目前零质量证据），同时解锁 prefer-capable 前置；(B) prefer-capable 加权调参——直接对能力位 provider 融合加权（无 eval 数据）；(C) dsh 宿主侧 live 验收（被用户环境阻塞）；(D) 审计返工批次（七项小修+治理形式宣告）。

调研问题：工业界检索质量评测的成熟心智模型——离线评测语料与判断集构建、NDCG/MRR/recall@k 类指标、LLM-as-judge 的证据等级与陷阱、interleaving/A-B 在线评测——对「先建评测面、后调融合/路由权重」这一排序的支持强度如何？无评测数据直接调融合/路由权重的先例与实证风险是什么？垂直领域检索评测（domain-specific retrieval evaluation，金融/医疗/代码等垂域基准）有哪些成熟先例与方法论？融合/路由层对特定 provider 的权重倾斜（capability-aware weighting / source selection weighting）在联邦检索与聚合搜索里有哪些成熟心智模型与已知陷阱？请给出 R84 主轴推荐与理由。
