### 心智模型 A：发布授权边界——「审批闸 vs 最后一寸 vs 全委托」

**调研支持的结论：**

1. **业界标准分法是「可编码的自动化，需判断的留人」**。Azure DevOps 官方文档把 Approvals（人审）、Gates（外部健康信号自动判定）、Manual Validation（人到现场执行手动步骤后放行）定义为三种可组合的层；其设计问答明确：「能完全用代码定义的检查→自动化；需要生产现场知识/时机判断/协调的→留人」（learn.microsoft.com，已读原文）。GitHub Environment 的 required reviewers 机制同构：job 引用受保护环境后必须等命名人类批准，且可开 prevent self-review（docs.github.com，已读原文）。

2. **人审的独有价值 = 问责 + 上下文判断**，不是多一道测试。可复核的记录「某人批准了这个变更并把名字签在上面」；技术指标（测试、扫描）机器做，时机/风险/影响判断人做。——Azure DevOps 文档 + AI agent 授权文献双重支持。

3. **AI agent 特有的授权收敛模式**（auth0.com 已读原文 + HN 生产者讨论已读原文）：
   - 权限按**能力范围（capability-scoped）**授出而非整体继承人类权限；
   - 高危动作**人工审批**、低危自主，即「conditional human approval——只在意图越线时触发复核」（HN 高赞回帖原话）；
   - 执行层与授权层分离，**enforcement point agent 不可绕过**；
   - 不可逆/外发动作（转账、退款、对外发布）是文献中公认最需要人闸的一类。「发布到公共 registry」正属此外发类：**不可逆（unpublish 政策严格受限）、面向全球公众、代表署名身份**。

**推理（我的判断）：** 三个候选放回这个模型里：

- **A（全委托）**：技术上流水线已具备 fail-closed（门红自动开 issue），agent 只是把按钮按到底。但 A 把「署名发布」这个唯一不可逆、唯一代表项目对外身份的动作交给了非确定性系统，且账本里没有任何条款预先授权 agent 扳外发扳机。业界没有找到「agent 全权执行首次公开生产发布」的成熟先例；文献方向一致反对。
- **B（最后一寸手动）**：恰好是「自动化全部可编码判定（gate 绿 = 技术判定）+ 人类做唯一需要判断/问责的动作（tag push = 签名）」的最小实现。且与你已立法的结构对齐：assert-checks-green 已把技术判定机器化，git push tag 本身就是签名行为。发布后验证（npm view / 陌生人安装）是只读动作，无外发风险，可以交回 agent 跑——B 方案里「停手点之后」建议改为：用户手动 push tag → publish 自动跑 → agent 继续执行发布后验证与报告。这样人只碰一次扳机，其余全程自动化。
- **C**：如 GitHub Environment required reviewers（发布 job 挂受保护环境等你在网页上批）或 protected tag ruleset。调研确认这套机制成熟，但对**单人项目**它只比 B 多一层 UI 仪式、少一分直达（你本来就在 gh 认证的终端边上），收益不抵配置成本。可作为未来多人协作时迁移目标。

**推荐 B，并把发布后验证划回 agent 职责。**

### 止血三件套（deprecate / advisory / release notes）怎么配

**调研支持的结论：** deprecate 触达「所有安装该版本的人」（终端警告 + npm 页红标，间接进 npm audit）；GitHub Security Advisory 触达「GitHub Advisory Database + Dependabot 告警」并同步到 npmjs.com/advisories——但那是为**安全漏洞**设计的（需 CVE、有 fix version 字段），且其纪律「披露前必须先有修复版本」与你先 publish 后 deprecate 的顺序一致。Release notes/CHANGELOG 触达看 repo 的人。

**推理：** 这条 404 死路由是**功能性缺陷**（默认端点失灵→开箱即坏），不是安全漏洞——按「'security' 留给真安全问题」的措辞纪律，**不建议发 Security Advisory**（会占用 advisory 通道的严肃性，还可能触发对下游库的 Dependabot 假警报）。三件套裁为两件套：**deprecate（精准版本）+ Release notes/CHANGELOG 一段「已知 0.0.x 缺陷说明」**。后者你发布轮本来就要写。
