# R92 Q2 调研题面 — T2 复跑凭证注入机制 + 宿主选型 + L3b 取证修订

## 背景（仓库 anysearch-cli，dsh 插件宿主验收）

上轮 R91 在真宿主 dsh 上做 L3 冒烟，判词 F-bug：L3a 装册绿 ESTABLISHED（dump-config 单行注册在位），L3b/L3c-min NOT-ESTABLISHED（根因=DEEPSEEK_API_KEY 缺失，环境缺位非机制故障）。本轮 R92 用户裁定主轴 A=售后收口续轮：注入自定义上游 https://api.featherless.ai/v1 + API key 后复跑 T2，绿了动 README verified-hosts 行（227/zh:217 现为过期表述 0.1.5-rc.2+MCP bridge）。

## 已实测的凭证/上游注入面（dsh 0.1.7-rc.2 本机全局安装）

1. dsh-base/cordis.patch.yml 默认模型路由：agent-default-model config {provider: deepseek-official, model: deepseek-flash}。
2. dsh-llm-deepseek 路由锁 Messages/Anthropic 协议（protocol is not configurable;默认 https://api.deepseek.com/anthropic）；存在 env DEEPSEEK_BASE_URL 可覆写端点（honored only from trusted layers）。
3. dsh-llm-pi-ai dormant 挂载：profile cordis.patch.yml 用户层供 config.providers.<name>={apiKeyEnv,api:'openai-completions',baseURL,models:[{id,contextWindow,reasoningEfforts?}]}即注册活路由；apiKeyEnv 经 credential seam 按名解析，值不落盘。
4. dsh 凭证链：env→credentials service（web Models 页写入）。headless 无 web 面。
5. Windows env 传播模型：进程 env=启动快照；用户级变量需 User-scope 读取注入子进程（已验证 DEEPSEEK_API_KEY User-scope SET len=67）。
6. featherless 端点面：GET /v1/models→404 Gone（带key/不带key均验证）；POST /v1/chat/completions 带 ANS_LLM_API_KEY→401（该 key 属本地迁移态端点非 featherless）。模型 id 无法 API 枚举。
7. R91 T1 取证通道判词：stream-json NDJSON 通道机制 ESTABLISHED；model-request tools 载荷可见性 NOT-ESTABLISHED（认证败在载荷生成前从未观察）。
8. npm dist-tags 漂移：latest=0.2.0-rc.2（=next），钉版线 0.1.7-rc.1；本机 dsh=0.1.7-rc.2。exact-build claim 原则=测到的版本才许写 README。

## 账本 current 决策（不得静默改向）

- R92 D-001：主轴=售后收口续轮完整版：T2 复跑（自定义上游+key）→达标启 README 对齐+readme-token claims 检查器接线+deprecate 执行尝试；宿主选型重裁；key 值不入档；一票一 commit；范围外=repin/垂域复核/web-matrix/评测面/常驻债。
- ADR-0092 D1（已立法）：门判据三腿 L3a 装册绿（确定性）/L3b 枚举绿（transcript model-request tools 载荷含五 ans_* 裸名+inputSchema）/L3c-min 执行绿（≥1 ans_* 完成 ans-mcp /mcp 往返，content 或 isError 皆算）；L3c-full 五工具诱导矩阵=增强判据不阻塞；诱导任务措辞跑前定死；N≤3；三分支判词；established/not-established 词汇锁定。
- ADR-0090 真值表+addendum：soak-until-stable；0.2.0 stable 晋升目击才触发收口探针；latest 指向 rc≠stable 晋升。

## 待裁问题（给出推荐+理由，工业界成熟心智模型重点）

Q-A 凭证注入机制：pi-ai 自定义路由（profile patch 层 providers 段+agent-default-model 覆写）vs DEEPSEEK_BASE_URL env 覆写（Messages 协议锁与 featherless OpenAI-completions 面兼容性疑点）vs 其他。子问题：profile 策略=新建隔离 profile（如 r92-smoke，L3a 冷启动全链复验）vs 复用 headless 改其 patch 层。
Q-B 宿主版本：0.1.7-rc.2（已装+钉版同线+R91 同环境连续性）vs 0.2.0-rc.2（latest=陌生人今日所得，但 R89 已证 0.2.0 线有 breaking-surface、钉版未动）。exact-build claim 下 README 行应记实测宿主——选哪个版本做本轮冒烟？
Q-C L3b 取证修订提案：若 transcript 仍不放出 model-request.tools 载荷，是否接受等价通道=transcript 中出现 ans_* tool_call 事件即证枚举发生（模型只能调用被枚举的工具）？还是保持 ADR-0092 原义 L3b=载荷显性可见？修订需走 revised 流程。
Q-D 凭证卫生：key 经 User-scope env→子进程注入、apiKeyEnv 名引用、值不落盘不落上下文——此做法与工业界 secrets-in-env/十二要素/CI secret 注入惯例的符合度？有无可取加强（如 launch-wrapper、env-scoped spawn）？
Q-E 模型 id 冻结程序：featherless 无 /v1/models 枚举——跑前定死模型 id 的合法来源（用户指定 vs 文档目录 vs preflight 多候选探针）与 tool-calling 能力要求的判定法。
